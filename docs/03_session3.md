## 1. よいルールとは

第2回では、3つの方式を動かしました。

- **人間中心**：危険な実行は起きないが、すべて人間が確認するので手間と時間がかかる
- **完全委譲**：速いが、AIの誤りがそのまま実行される

判断DSLは、この中間をねらいます。ルールが人間を呼ぶか（`ask_human`）、AIに任せるか（`auto`）を、**あなた自身の判断**（承認するか、却下するか）と比べると、4つの場合に分かれます。

|  | ルール → `auto`（任せる） | ルール → `ask_human`（人間を呼ぶ） |
|---|---|---|
| **あなたなら承認する** | ○ 任せてよい | △ 余計な確認（手間が増える） |
| **あなたなら却下する** | **× 危険（誤りがそのまま実行される）** | ○ 正しく止めた |

- 「×危険」を減らそうとして人間を呼びすぎると、「△余計な確認」が増えます。
- 「△余計な確認」を減らそうとして任せすぎると、「×危険」が増えます。

**この2つのバランスをどう取るか**が、今日の設計の中心です。どちらをどれだけ重く見るかにも、正解はありません。理由を説明できることが大切です。

### 設計で気をつけること

1. **順番が大事**：ルールは上から順に調べ、最初に当てはまったものだけが使われます（`docs/dsl_spec.md` の第2節）。
2. **アラートを覚えるのではなく、「型」で書く**：第4回の実験では、**まだ見ていない新しいアラート**が加わります。「A03 なら任せる」のようなルールは書けませんし（IDは条件に使えません）、A01〜A05 だけにぴったり合わせたルールは、新しいアラートでは外れるかもしれません。「どんな対応か」「どれくらい重要な機器か」「AIはどれくらい自信があるか」といった**性質**で書きましょう。
3. **AIの自信（`confidence`）はAIの自己申告**：第1回で、同じアラートでも自信の値が毎回変わることを見ました。それに頼りすぎてよいかも考えましょう。

## 3. ステップ1：自分の判断表を作る

まず、例のルールで試してみます。

```bash
python s3_check.py rules/example.yaml
```

このプログラムは、第1回・第2回で**AIが出したすべての提案**を集めて、「あなたなら承認するか」を聞いてきます。

- 第2回の「人間中心」で承認・却下したものは、その答えが自動で使われます。
- まだ判断していない提案だけを聞かれます。`y`（承認）か `n`（却下）で答え、理由をひとこと入力します。
- **第1回の演習の表**（承認する／しない、その理由）を見ながら、同じ考え方で答えましょう。

答えは `results/my_judgments.csv` に保存され、次からは聞かれません（Excel で開いて直すこともできます）。この表が、今日の「答え合わせ」の基準になります。

すべて答えると、次のような結果が出ます。

```
ルール「判断DSLの例」を、AIの提案 12 件に当てはめた結果

                ルール → auto         ルール → ask_human
  あなた承認     ○ 任せてよい    3   △ 余計な確認    4
  あなた却下     × 危険          1   ○ 正しく止めた   4

  人間を呼ぶ割合: 8/12（67%）    危険: 1 件

× 危険：あなたなら却下するのに、そのまま実行されるもの
  A03  block_ip → 10.0.5.20  自信=0.75  [すぐ元に戻せる対応はAIに任せる]  あなたの理由: 定期診断

△ 余計な確認：あなたなら承認するのに、人間が呼ばれるもの
  ...

どのルールが何回使われたか（上から順に調べて最初に当たったもの）
  ...
```

（数字は一例です。）同じ提案は1つにまとめて数えます。AIが `escalate` した提案は、どのルールでも人間が決めるので数えません。

人間中心と完全委譲でも試して、両極端の結果を見ておきましょう。

```bash
python s3_check.py rules/human_centered.yaml
python s3_check.py rules/full_delegation.yaml
```

## 4. ステップ2：自分のルールを書く（個人）

例のルールを写して、自分のファイルを作ります（ファイル名は英数字で）。

```bash
cp rules/example.yaml rules/my_rules.yaml          # Windows は copy rules\example.yaml rules\my_rules.yaml
```

`rules/my_rules.yaml` をエディタで開き、書き換えます。書き方は `docs/dsl_spec.md` を見てください。

**書く → 確かめる → 直す** をくり返します。

```bash
python s3_check.py rules/my_rules.yaml
```

### 考えるヒント

第1回のまとめで、次の3つのタイプがあることに気づきました。それぞれ、どの項目で見分けられるでしょうか。

| タイプ | 例 | 使えそうな項目 |
|---|---|---|
| AIに任せてもよさそう | 被害が小さく、すぐ元に戻せる対応 | `action` |
| 必ず人間が確認すべき | 業務が止まる対応、人の処遇に関わる対応、重要な機器 | `action`、`asset.importance` |
| 急ぐので人間を待てない | 被害が刻一刻と広がる攻撃 | `severity`、`verdict` …？ |

- 「急ぐので人間を待てない」は、ルールで書けるでしょうか。書けるとしたら、それはどんな危険と引き換えでしょうか。
- 書きたいのに、**使える項目がなくて書けない条件**はありましたか？（例：「対象が多いとき」「元に戻せない対応のとき」）　メモしておいてください。第5回の分析で使います。

## 5. ステップ3：班で1つのルールにまとめる

第4回の実験では、**班で1つに決めたルール**を「判断DSL」の条件として使います。

1. 各自の `s3_check.py` の結果（「×危険」の件数、「人間を呼ぶ割合」）を見せ合う
2. 各自のルールのよいところを持ち寄って `rules/team.yaml` を作る
3. 全員の判断表で確かめる（各自の手元で `python s3_check.py rules/team.yaml`）

人によって判断表が違うので、同じルールでも結果が変わります。**誰の判断を基準にするか**も話し合いましょう。

## トラブルシューティング

| 症状 | 対処 |
|---|---|
| `results/ に第1回・第2回のCSVがありません` | `code` フォルダで実行しているか確認する。第1回・第2回のCSVが `results/` にあるか確認する |

| 「同じ提案」が何度も聞かれる | 対象（`target`）の書き方がAIの回答ごとに少し違うと、別の提案として扱われます。同じ考え方で答えれば問題ありません |
