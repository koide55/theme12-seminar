## 2. 設計指針をつくる（班で）

**設計指針**とは、「こういうときは、AIに任せてよい／人間が承認する／人間が先に決める」という、ほかの組織でも使える**一般的なきまり**です。アラートのIDではなく、**判断の性質**で書きます。

### 書き方

> **〔条件〕のときは、〔AIに任せる／人間が承認する／人間が先に決める〕べきである。**
> なぜなら、〔理由〕。私たちの実験では、〔根拠となる数字やアラートの例〕。
> ただし、〔例外や注意〕。

例（このまま使わず、自分たちの結果で書いてください）：

> **元に戻せて影響が小さい対応（IPアドレスの遮断、監視の強化）は、AIに任せてよい。**
> なぜなら、誤っても被害が小さく、すぐ取り消せるから。私たちの実験では、A06 の `block_ip` を自動にしても誤りは増えず、介入率は ○% 下がった。
> ただし、遮断する相手が取引先など業務に必要な相手のときは、この限りではない。

### 観点のヒント

次の観点から、少なくとも**3つ**の指針を作りましょう。

| 観点 | 問い | 関係しそうなアラート・結果 |
|---|---|---|
| 元に戻せるか | 誤ったとき、すぐ取り消せるか | `block_ip` と `isolate_host` の違い |
| 影響の大きさ | 何台・何人・どの業務に影響するか | A08、A09、承認なし実行 |
| 人への影響 | 人の処遇（処分・疑い）に関わるか | A05 |
| 緊急性 | 人間を待つ間に被害が広がるか | A04、1件の平均秒 |
| AIの自信 | 自信の値は当てになったか | 自信 < 0.7 のルール、モデルごとの自信 |
| 文脈 | AIはアラートの背景を読めたか | A03、A07、A09 |
| AIの強さ | 強いAIなら任せる範囲を広げてよいか | 第5回のモデル比較 |
| 人間の限界 | 人間に回せば必ず正しくなるか | 人間が誤らせた件、人間中心の成功率 |

### 指針の確かめ方

作った指針をルール（YAML）に書き直せるものは、`rules/guideline.yaml` に書いて確かめましょう。

```bash
python s5_whatif.py rules/team.yaml rules/guideline.yaml
python s5_models.py compare rules/guideline.yaml
```

ルールに書けない指針（例：「人間に見せる情報を増やす」）は、それで構いません。**なぜルールでは書けないのか**を説明できるようにしておきましょう。

## 3. 限界を考える

結果を発表するときは、**どこまで言えて、どこから先は言えないか**をはっきりさせることが大切です。次の点について、班で話し合ってください。

- **データの量**：アラートは10件、承認者は数人です。数字の違いは偶然かもしれません。
- **模擬データ**：アラートは架空で、正解は教員が決めたものです。本物のSOCでは、アラートの数も種類もずっと多く、正解が分からないことも多いです。
- **承認者の慣れ**：同じ人が3つの条件で同じ提案を見ています（順番を変えて打ち消そうとしましたが、完全ではありません）。
- **第5回の計算の仮定**：ルールを変えたときの結果は、人間中心での判断を使った「目安」です。
- **AIの変化**：モデルが変われば結果は変わります。同じモデルでも、毎回同じ答えとは限りません。

### 構成の目安（発表時間は教員の指示に従う。10分なら8〜10枚）

### グラフをつくる

CSVは Excel や Google スプレッドシートで開けます。おすすめのグラフ：

| グラフ | 使うファイル | 形 |
|---|---|---|
| 条件ごとの結果 | `s4_score.py` の出力（表を写す） | 棒グラフ（成功率・介入率を並べる）。承認なし実行は件数で横に添える |
| ルールのトレードオフ | `session5_whatif.csv` | 散布図（横軸 `intervention_rate`、縦軸 `success_rate`、点ごとにルール名） |
| モデルの比較 | `session5_models.csv` | 棒グラフ（モデルごとの `ai_success_rate` と、ルールごとの `intervention_rate`） |

グラフには、**軸の名前と単位**、**何件のデータか**を必ず書きましょう。

## 5. レポート

レポートは `docs/report_template.md` の構成に沿って書きます（分量・形式・締め切りは教員の指示に従う）。発表と同じ内容でかまいませんが、レポートでは次の点を**より詳しく**書きます。

- 自分が承認者として判断したときに考えたこと（`human_note` に書いた理由も使える）
- 班の設計指針に対する、**自分自身の意見**（賛成か、どこを変えたいか）

## 6. 発展（時間があれば）

- **新しいアラートを作る**：自分たちのルールの「穴」を突くような模擬アラートを作り、AIに判断させてみましょう。`data/alerts.json` と同じ形式で `data/my_alerts.json` に書き、次のように実行します（IPアドレスは `203.0.113.0/24`、`198.51.100.0/24` などの文書用の範囲を使い、実在の組織名は使わない）。
  ```bash
  python s1_agent.py --data ../data/my_alerts.json --repeat 3
  ```
- **AIに返させる項目を増やす**：第3回で「書けなかった条件」（対象の数、元に戻せるか など）を、`s1_agent.py` の `SCHEMA` に項目として追加すると、ルールで使えるようになるでしょうか（`dsl.py` の `FIELDS` も変える必要があります）。

## 7. まとめ

- 「AIに任せるか、人間が決めるか」は、**AIの正しさだけでは決まりません**。元に戻せるか、影響の大きさ、人への影響、緊急性、そして人間の判断の限界を合わせて考える必要がありました。
- 判断DSLは、その考えを**ルールとして書き、データで確かめる**ための道具でした。
- AIが強くなっても、どこで人間が責任を持つかを**設計する**ことは残ります。
